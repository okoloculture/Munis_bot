# Munis Price Bot

Зеркалирует прайсы из оптового канала в розничный, пересчитывая цены по ступенчатой наценке.

- **Источник:** `@opt_uniseil` (ЮНИСЕЙЛ ОПТ) — читается через публичное веб-превью `t.me/s/`, без userbot и без API-ключей Telegram.
- **Приёмники:** три канала на одном коде — `MUNIS_PRICE` (`-1004494948640`), `IStore ima`
  (`@imastoreeee`) и `Price` (`-1004374090427`). У каждого свой конфиг и своё состояние;
  Price ведёт тот же бот, что и MUNIS.

| Канал | Конфиг | Состояние | Токен | Наценка | Вид постов |
|---|---|---|---|---|---|
| MUNIS_PRICE | `config.yaml` | `state.json` | `BOT_TOKEN` | абсолютная, в рублях | текст |
| IStore ima | `config-ima.yaml` | `state-ima.json` | `BOT_TOKEN_IMA` | процентная | текст |
| Price | `config-price.yaml` | `state-price.json` | `BOT_TOKEN` | как у MUNIS | таблицы |

Имя переменной с токеном задаётся ключом `bot_token_env`, поэтому добавить ещё один
канал — это новый конфиг плюс шаг в workflow, без единой правки кода.

## Таблицы (Rich Messages)

`message_format: rich` публикует каждую категорию одним постом-таблицей
`Категория | Цена` через `sendRichMessage` (Bot API 10.1+). Rich-пост вмещает
до 32768 символов текста против 4096 у обычного, поэтому даже Samsung помещается
в один пост. Правятся такие посты тем же `editMessageText` с полем `rich_message`,
ошибки `not modified` и `not found` приходят те же, что у обычных сообщений.
Обычный пост правкой превращается в rich и обратно — поэтому сдвиг инфо и
навигации (см. «Информационное сообщение») работает и тут.

Сдвоенная категория опта (`iPhone 17e \ 17`, `Watch SE \ S10 \ S11 \ S12`)
раскладывается внутри поста на отдельные таблицы по моделям — модель строки
узнаётся по первым словам. Модель из заголовка, которой сейчас нет в опте,
получает таблицу «Цена по запросу»; так же заменяется строка опта «Товары не найдены».

`tidy_names: true` приводит названия к виду для покупателя (правила — в `names.py`):
тип техники в начале (`iPhone 17e 256GB …`, `Apple Watch S11 …`), у макбуков
заводской код уходит в конец, а из конфигурации остаются память и накопитель:
`MHFD4 Neo Citrus A18 Pro (6/5/8/256)` -> `MacBook Neo Citrus A18 Pro 8/256 (MHFD4)`.

Переключать формат у канала, где посты уже есть, можно: следующий прогон
перепишет их таблицами, но число постов на категорию останется прежним.

## Важное ограничение Telegram

Bot API **не даёт боту править сообщения, отправленные не им** — даже с админ-правом
«Редактирование сообщений» (`can_edit_messages`) ответ будет `Bad Request: MESSAGE_ID_INVALID`.
Проверено на живом канале. Поэтому бот работает только со своими постами: при первом запуске
создаёт их сам, дальше редактирует. Забрать чужой прайс-лист под управление невозможно.

## Как это работает

1. Каталог источника — блок сообщений с заголовком `📦 <Категория>` и опциональным `(часть N/M)`.
   Источник периодически перепубликовывает весь блок заново, поэтому `message_id` меняются —
   категории определяются по заголовку, а не по захардкоженным id.
2. Строки прайса переносятся **дословно**: меняется только число цены в конце строки.
   Названия, флаги, пометки `(Уценка)`, пустые строки-разделители сохраняются как есть.
3. Контент категории раскладывается по сообщениям, закреплённым за ней в `state.json`.
   Новой категории отводится столько сообщений, сколько частей у неё в источнике;
   дальше это число фиксируется, и контент перебивается под него.
4. Хеш содержимого хранится в `state.json`: неизменившиеся категории не трогаются.
5. Все позиции дополнительно выгружаются в `.xlsx` на диск; заливка файла в канал — по флагу.
6. Перед навигацией публикуется информационное сообщение из `info.html`.
7. Навигационное сообщение с кнопками пересобирается после каждого прогона и закрепляется.

## Наценка

Ступень задаётся либо `add` (прибавка в рублях), либо `pct` (процент от закупки),
но не обоими сразу. `up_to` — верхняя граница включительно. У MUNIS наценка абсолютная:

| Закупка до | Наценка |
|---|---|
| 10 000 | 2 000 |
| 15 000 | 3 000 |
| 40 000 | 4 000 |
| 80 000 | 5 000 |
| 110 000 | 6 000 |
| 135 000 | 7 000 |
| 160 000 | 8 000 |
| 185 000 | 9 000 |
| остальное | 13 000 |

У канала ima наценка процентная, как была в прежнем боте:

| Закупка до | Наценка |
|---|---|
| 40 000 | 10% |
| 70 000 | 7% |
| 100 000 | 6% |
| остальное | 5% |

Проценты дают некруглые числа, поэтому там включено округление вверх до сотен.

## Установка

```bash
python3.12 -m venv .venv
.venv/bin/pip install -r requirements.txt
cp .env.example .env      # и вписать BOT_TOKEN
```

## Права бота

Бот должен быть админом целевого канала с правами:

- **Публикация сообщений** — создать посты при первом запуске;
- **Редактирование сообщений** — обновлять их дальше; в каналах это же право
  разрешает закреплять, отдельная галочка «Закрепление» не нужна;
- **Удаление сообщений** — не обязательно, пригодится для ручной чистки.

## Запуск

```bash
.venv/bin/python main.py --dry-run   # собрать сообщения в ./_dryrun, ничего не публикуя
.venv/bin/python main.py --excel     # собрать только .xlsx, канал не трогать
.venv/bin/python main.py --once      # один прогон с публикацией (MUNIS_PRICE)
.venv/bin/python main.py --once --config config-ima.yaml --state state-ima.json
.venv/bin/python main.py             # демон: синхронизация каждые check_interval секунд
```

Первый `--once` создаёт все посты и навигацию (~43 сообщения, около трёх минут:
Telegram пускает бота примерно 20 новых сообщений в минуту). Дальше правки идут
только по изменившимся категориям. Токен для `--dry-run` не нужен.

`--seed` подхватывает уже готовые посты из **публичного** целевого канала, если бот
их же и отправлял. Для приватного канала и для чужих постов не работает.

`state.json` — единственная связь бота с каналом. Удалите его, и следующий запуск
опубликует весь каталог заново, а старые посты останутся сиротами.

## Конфигурация

Всё в `config.yaml`; секреты — в `.env`.

| Ключ | Смысл |
|---|---|
| `source_channel` / `target_channel` | username каналов без `@` |
| `target_chat_id` | что уходит в Bot API: `@username` или числовой `-100…` |
| `markup_tiers` | ступени наценки |
| `round_to_nearest` | округление итоговой цены вверх: `0` — не округлять |
| `check_interval` | период синхронизации, секунды |
| `max_scan_pages` | глубина листания истории канала (20 сообщений на страницу) |
| `categories` | упорядоченный список категорий; задаёт и состав, и порядок постов |
| `deny_categories` | чёрный список поверх `categories` |
| `allow_create` | разрешить создавать сообщения; обязательно для пустого канала |
| `price_format` | шаблон строки, `{name}` и `{price}` |
| `message_format` | `text` — обычные посты, `rich` — таблицы Rich Messages |
| `tidy_names` | названия для покупателя в rich-постах (тип техники, код макбука в конце) |
| `nav.enabled` / `nav.text` / `nav.pin` / `nav.button_style` | навигационное сообщение |
| `nav.columns` / `nav.row_width` | раскладка кнопок: максимум штук и символов на ряд |
| `order_button.text` / `order_button.url` / `order_button.style` | кнопка под каждым постом и внизу навигации |
| `info_message.enabled` / `info_message.file` | информационное сообщение перед навигацией |
| `excel.enabled` / `excel.output_dir` / `excel.filename` | сборка прайса в .xlsx на диск |
| `excel.publish` / `excel.button_text` / `excel.button_style` | заливка файла в канал и кнопка на него |

Переменные окружения: `BOT_TOKEN` (обязательно), `TG_PROXY` (SOCKS5/HTTP-прокси для всего трафика Telegram).

## Цвет кнопок

`InlineKeyboardButton` принимает поле `style`. Список значений проверен запросами
к живому Bot API — вопреки части статей в сети, `positive` и `negative` он отвергает:

| `style` | Вид |
|---|---|
| `default` | обычная серая (значение по умолчанию, в запрос не подставляется) |
| `primary` | синяя заливка |
| `success` | зелёная |
| `danger` | красная |

Задаётся отдельно для кнопок категорий (`nav.button_style`) и для кнопки заказа
(`order_button.style`). Смена стиля меняет хеш категории, поэтому применяется
на ближайшей синхронизации ко всем постам сразу.

## Информационное сообщение

Текст лежит в `info.html` — часы работы, адрес, гарантия, контакт отдела продаж.
Правится в файле, конфиг трогать не нужно; разрешена HTML-разметка Telegram
(`<b>`, `<i>`, `<u>`, `<s>`, `<a href>`, `<code>`, `<pre>`). Лимит — 4096 символов,
более длинный текст бот не отправит и напишет об этом в лог.

Сообщение идёт предпоследним, сразу за прайсами и перед навигацией. Telegram
не умеет переставлять сообщения, а свои посты старше 48 часов бот удалить не может
даже с правом «Удаление сообщений». Поэтому порядок держится сдвигом, а не удалением:
новый прайс-пост занимает информационное сообщение, информационное — навигацию,
и новой в конец канала уходит только навигация (старая при этом открепляется,
новая закрепляется). Ссылки в кнопках не ломаются — они ведут на первые части
категорий, а те никуда не переезжают.

## Если сообщение удалили из канала руками

Бот это видит по ответу `message to edit not found` и забывает этот `message_id`.
Пропавшая часть категории сначала раскладывается по оставшимся её сообщениям, а что
не влезло — уходит в новый пост тем же сдвигом, что описан выше. Удалённые руками
информационное сообщение или навигация создаются заново.

## Выгрузка в Excel

При `excel.enabled: true` бот собирает книгу со всеми позициями и кладёт её в
`excel.output_dir`. В канал файл **не уходит** — за это отвечает отдельный флаг
`excel.publish` (по умолчанию выключен). Лист один:
`Категория | Наименование | Цена, ₽`, с автофильтром и закреплённой шапкой; цена —
число, а не текст, поэтому по ней работают сортировка и формулы.

Собрать файл отдельно, ничего не трогая в канале: `python main.py --excel`.
Токен для этого не нужен.

При `excel.publish: true` файл дополнительно заливается в канал и в навигации
появляется кнопка со ссылкой на него. Тогда сравнивается хеш **позиций**, а не
байтов книги — два .xlsx с одинаковым содержимым всё равно различаются байтами
из-за времени создания, и по байтам файл перезаливался бы каждый час впустую.
Обновляется то же сообщение через `editMessageMedia`, новых в канале не появляется.

`excel.filename` понимает подстановку `{date}` — дата по Москве на момент сборки.

## Раскладка кнопок навигации

Telegram растягивает кнопки одного ряда на равную ширину, поэтому длинная подпись
рядом с короткими сминается. Ряд набирается по двум пределам сразу: не больше
`nav.columns` кнопок и не больше `nav.row_width` символов подписей. Что наступит
раньше, то и закрывает ряд, а слишком длинная подпись занимает ряд целиком.

При 27 категориях и `columns: 3`, `row_width: 30` получается так: бренды по три
в ряд, модели iPhone по две, `Watch SE \ S10 \ S11` и `iPad Mini \ 10 \ 11` — по одной.

## Что происходит при переполнении

Если позиций стало больше, чем влезает в отведённые сообщения:

- `allow_create: false` (по умолчанию) — хвост списка скрывается, в конец добавляется
  строка «… ещё N позиций — уточняйте у менеджера», в лог уходит WARNING;
- `allow_create: true` — бот добавляет сообщения над информационным и навигацией
  (см. «Информационное сообщение»), навигация пересобирается сама.

## Развёртывание

Бот живёт в GitHub Actions, своего сервера не нужно: `.github/workflows/sync.yml`
запускает `main.py --once` раз в час и коммитит обновлённый `state.json` обратно
в репозиторий. Токен лежит в Secrets репозитория под именем `BOT_TOKEN`,
в код и в `.env` репозитория он не попадает.

- Запустить вручную: вкладка Actions → sync → Run workflow, или `gh workflow run sync.yml`.
- Поменять расписание: строка `cron` в workflow, время в UTC.
- Свежий `.xlsx` каждого прогона лежит в артефактах, хранится 14 дней.
- `concurrency` не даёт двум прогонам пересечься и затереть `state.json`.

`state.json` намеренно **не** в `.gitignore` — это единственная память бота о том,
какие сообщения канала он ведёт. Потеряется он — следующий прогон опубликует
весь каталог заново, а старые посты останутся сиротами.

GitHub отключает расписание в репозиториях без активности 60 дней. Бот коммитит
`state.json` при каждом изменении цен, так что в норме это не грозит, но если
канал надолго замрёт — проверьте, что workflow не усыплён.
